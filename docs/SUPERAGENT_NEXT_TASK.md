# TaskFlow 第二阶段：依赖图与完整可观测性

## 任务目标

在现有 TaskFlow 基础上，实现“200+ 任务、2000+ 事件时仍正确的工作流观察台”。保留现有业务不变量、持久化执行和全部有效测试。不要重建项目或替换成静态演示。

## 工作内容

### 1. 正确的全量统计

增加项目统计 API，数据库端聚合全部任务状态、阻塞任务和 Run 状态；UI 使用这个 API，而不是读取最近 100 个任务再计算。

验收：隔离测试创建 205 个任务，其中 101 个 done；分页看板只加载一页，概览仍显示准确的项目总数和完成数。说明阻塞统计是否包含 canceled/done 并保持一致。

### 2. 最新活动和审计分页

增加事件查询的倒序游标分页、任务/Run 筛选，同时保留现有正序 after 与 SSE Last-Event-ID 语义。事件保留稳定顺序，翻页不重复、不漏掉边界事件。

UI 的最近活动必须显示真正最新的事件；任务详情能翻看其完整审计，而不是对项目最早 1000 条本地过滤。

验收：数据库中创建超过 2000 条混合任务事件，最新一条仍能立即显示；前后分页和 SSE 重连有实际测试。

### 3. 可搜索的依赖选择

任务表单改为服务端搜索与分页，不限制为最近 100 个任务。编辑时保留未加载的已选项。提交重复、跨项目或成环依赖仍由后端拒绝。

验收：可以选择和移除第 150 个任务；先选多个任务，再切换搜索条件，已选项不会静默丢失。

### 4. 依赖图

提供基于实际数据库关系的项目 DAG 视图。支持状态/优先级标识、缩放、平移、搜索定位和点击节点打开现有任务详情。突出当前任务的前置链和未完成阻塞节点。

可以使用合适的图形库；禁止把数据库关系手工写成静态 SVG。处理长标题、独立任务、分支汇聚和空项目。至少验证 200 个节点时没有页面布局溢出。

### 5. Run 的尝试历史与导出

目前 Run 的 steps 只保留最后一次尝试。增加迁移和数据结构，保存每次 attempt 的开始/结束时间、每步开始/结束时间及错误分类，取消和中断也有明确结果。

提供单次 Run 的 JSON 导出，包含 task/run/attempt/step/audit 的关联 ID 与必要业务数据，不包含环境变量、凭据或 Harness 原始 Session。

界面能区分尝试次数、排队等待和实际执行耗时；已取消/失败的步骤不能一直显示旋转的执行中图标。

验收：可重试执行器失败两次、第三次成功，完整保留三次尝试，导出后能按记录重建该 Run 的时间线。

## 工程要求

- 先阅读 AGENTS.md、README、ARCHITECTURE 和现有测试，报告实施计划并持续执行。
- 数据结构变化必须给已有 SQLite 数据库提供显式版本迁移，不能要求删除数据重建。
- 使用当前技术栈与包管理器。对 web/main.tsx 做适当组件拆分，避免继续堆叠单文件。
- 增加有意义的回归测试，运行 npm run check、npm run test:e2e 和 git diff --check。
- 浏览器测试使用临时数据库，不触碰用户演示数据。性能/规模验证不要依赖外部服务或额外付费 API。
- 更新文档与已知限制；不要把尚未验证的能力写为通过。

## Git 与飞书交付

在工单独立的 agent/ 分支实现，创建有意义的提交，推送并创建 Draft PR。不要直接推 main，不要合并或标记 ready for review。

最终在来源飞书话题报告：实际功能、迁移验证、测试命令与结果、未完成项、commit SHA、Draft PR URL、工单与 Worker Session 标识。遇到真正阻塞可说明所需信息，常规实现选择自行完成。
